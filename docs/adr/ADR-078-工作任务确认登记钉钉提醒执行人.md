| 日期 | 2026-09-03 |

---

## 1. 背景

内容计划 **启动**（FR-M2-009）已走 ADR-026 / ADR-060 §5.4：`ContentPlanServiceImpl.start` → `NotificationService.notifyPlanStarted` → 每条 PENDING task 的执行人收到 `TASK_PENDING`（站内 + 钉钉工作通知）。

工作任务 **确认登记**（FR-M2-010 · ADR-074）同样把 `oa_task` 置为 `PENDING` 且 `visible_in_list=1`，但 **不创建** `oa_content_plan`，`plan_id = NULL`。`notifyPlanStarted` 按 `planId` 查 task，**不能**直接套用。jingcai 异步 Job（ADR-077）也 **不**发通知。

产品要求：确认登记后，任务执行人与计划启动一样收到钉钉/站内待办提醒。

---

## 2. 决策（Accepted）

| # | 决策 |
|---|------|
| **D1** | **触发**：`POST /ops/work-task/sheet/confirm` **成功**且本批 task 已插入之后。与任务变 `PENDING` **同一时刻**（事务提交后），**不是** jingcai 完成时。 |
| **D2** | **接收人**：本批生成的每条 `oa_task.assignee_id`（SOP 节点 `executor_role` → `resolveAssignee`，无匹配 → IP 组长；ADR-074 **D7**）。登记行 `assignee_id` **不**作为接收人。 |
| **D3** | **通道 / 事件类型**：复用 ADR-026 **`TASK_PENDING`**（站内 `sys_message` + 钉钉工作通知 + 可选机器人降级）。**不**新增 dict / `NotificationEventType`。 |
| **D4** | **禁止**对工作任务调用 `notifyPlanStarted(planId)`。新增 `notifyWorkTasksPending(tenantId, tasks)`（或等价），**入参为已插入的 task 列表**，不按 `plan_id` 查询。 |
| **D5** | **基数 / 去重**：与计划启动一致 — **每条 PENDING task 一条消息**（同一执行人多节点 → 多条）。`biz_key = task:{id}:PENDING`（ADR-026 §3）；`tryClaimEvent` 去重，重复 confirm 静默跳过。 |
| **D6** | **Football 身份（ADR-056）**：`assignee_id` 已是写入侧 `resolveStorableUserId` 结果；通知侧沿用计划启动路径 `AdminUserApi.getByIds` 解析 `dingtalk_user_id`。禁止硬编码 userId/tenantId。 |
| **D7** | **韧性**：钉钉 / 站内 / Feign **失败不得回滚 confirm**（sheet 仍 CONFIRMED，task 仍 PENDING）。实现：confirm **afterCommit** 再发通知（不把钉钉 HTTP 放进 confirm TX）；外层 try/catch。缺失 `dingtalk_user_id`：跳过工作通知并 warn（ADR-026）。 |
| **D8** | **文案**：标题仍为「【运营平台】新任务待执行」。正文首句改为「工作任务登记已确认。」（无计划名）；任务名仍用 SOP 节点名。跳转 `/production/task`（同计划启动）。 |
| **D9** | **withdraw**：**不**发「取消通知」、不删已发站内/钉钉。与计划撤回一致（现网 start 无 un-notify）。Out of Scope。 |
| **D10** | **ADR-077 jingcai Job**：**不**额外发钉钉。自动草稿 / AI 成败与本通知无关。 |

## 3. 与既有 ADR 的关系

| ADR | 关系 |
|-----|------|
| **ADR-026** | 复用 `TASK_PENDING`、双通道、`biz_key`、凭证 `sys_param`。本 ADR 把触发面从「仅计划启动」扩到「工作任务 confirm」。 |
| **ADR-060 §5.4** | 钉钉恢复 carve-out 仍有效；本 ADR 是同一通道的第二个业务入口。 |
| **ADR-074** | confirm 全节点 task、`plan_id=NULL`、assignee 按岗位 **不变**。本 ADR 只加 confirm **侧效应**通知。 |
| **ADR-077** | afterCommit jingcai **不变**；**不**在 Job 里发通知。confirm HTTP 仍立即成功。 |
| **ADR-056** | 执行人 id 写入/解析规则不变。 |

## 4. confirm 侧效应伪代码

```
// confirm TX（ADR-074/075/077 不变）
createdTasks = []
for each assignment / execution group:
  for each SOP node:
    task = insert oa_task(..., plan_id=NULL, status=PENDING, assignee_id=resolveAssignee(...))
    createdTasks.add(task)
    // CONTENT_GENERATION：同 TX 建 DRAFT（ADR-077）
sheet = CONFIRMED（或部分确认规则不变）

afterCommit:
  enqueue jingcai(autoDraftContentIds)          // ADR-077 D7；不发钉钉
  try:
    notificationService.notifyWorkTasksPending(tenantId, createdTasks)
    // 每 task：tryClaimEvent(TASK_PENDING, task:{id}:PENDING, assignee_id)
    // 站内 + 钉钉（getByIds → dingtalk_user_id）
  catch:
    log.warn; // confirm 已成功
```

---

## 5. API / 响应

- 路径、权限、响应字段 **不新增**（仍 `sheetId` / `generatedTaskCount` / `confirmedAt`）。
- 侧效应写入 API 文档：confirm 成功后 afterCommit 对每条新 PENDING task 的 `assignee_id` 发 `TASK_PENDING`。
- 钉钉未配置 / 失败：**HTTP 仍 200**，sheet 已确认。

---

## 6. Out of Scope

- 新事件类型、新 Flyway、新 dict。
- jingcai 完成/失败时再通知。
- withdraw「撤回通知」。
- 计划启动改 afterCommit（保持现网 `start` 内 try/catch）。
- 按执行人合并为一条钉钉（与计划启动基数不一致，禁止）。

---

## 7. 验收（本 Slice）

- confirm 后对每条新 task 的 `assignee_id` 调用 `notifyWorkTasksPending`（`TASK_PENDING`）。
- `plan_id=NULL` 的 task 可通知（不依赖 planId）。
- notify 抛错 / 钉钉失败 → confirm 仍成功。
- jingcai Job 不调用通知。
- 无新 Flyway。
